# Scout Passport — Specification

A digital passport for our scout troop: profile, patrol, achievements, calendar,
and a recurring multiple-choice challenge game with leaderboards and push
notifications.

Internal tool for one troop. Not a product, not multi-tenant, not for sale.

> Items marked **[ASSUMED]** are defaults I chose so work could continue.
> Overrule any of them and I'll adjust.

---

## 1. Scope

### In scope

- Scout profile ("passport"): name, patrol, section, points, rank
- Achievements: fully customisable set, awarded by leaders with a completion date
- Calendar of events at three levels: troop, section, patrol
- Challenges: multiple-choice questions unlocked on a schedule, auto-marked
- Leaderboards: individual and patrol-vs-patrol
- Push notifications for new challenges, upcoming events, and announcements
- Meeting review by leaders: attendance, uniform check, and game points
- Leader admin for all of the above
- Useful info pages (uniforms, packing lists, safety), written by leaders
- Bilingual UI: Greek and English
- Installable to the home screen (PWA)

### Explicitly not in scope

- Profile photos or any image of a scout
- Subs/payments, parent accounts, messaging between scouts
- Multi-troop support, public sign-up, anything commercial
- Native iOS/Android apps

## 2. Users and roles

Three roles, one login screen, one app.

| Role | Can do |
|---|---|
| **Scout** | The scout app: passport, calendars visible to them, challenges, leaderboards |
| **Leader** | **No scout app.** A brief profile tab, then only management screens for **one assigned sector** — its scouts, review, badges, announcements, and challenge authoring scoped to that sector |
| **Troop Leader** | The same management app across **all sectors**, and the only role that can assign sectors or appoint leaders |

### Scope — what a leader can reach

Every leader is assigned a **sector**: the whole troop, a section, or a single
patrol. That assignment is the filter on everything they see:

| Screen | Leader (patrol sector) | Troop Leader |
|---|---|---|
| Scouts | Only their patrol, titled "My scouts" | Every patrol, plus the leader roster |
| Events | Their own patrol events are editable; troop and section events show a 🔒 read-only pill | All events, can create any |
| Review (attendance / uniform / points) | Only their own scouts | Anyone |
| Badges | Can award to their own scouts | Anyone |
| Challenges | Sees **only their sector's challenges**, and **can author new ones, locked to that sector** | Sees and authors across all sectors; each list row shows which sector it targets |
| Announcements | Their sector only | Any audience |
| Roles & permissions | Not visible | Only place sectors are assigned |

Challenges therefore carry a target sector (`section_id` already in the schema,
extended with a nullable `patrol_id` the same way `events` scope). A scout sees
a challenge if it targets the troop, their section, or their patrol; sector
leaders' authoring UI has the sector pre-filled and not editable.

**Only the Troop Leader can change roles.** The Roles screen does not appear at
all for anyone else — it is not a disabled button, it is absent.

A leader's own profile is deliberately thin — name, role, assigned sector, a
language toggle, and log out. **Leaders have no passport**: no points, no badges,
no rank, and they are excluded from leaderboards.

Current size: ~18 scouts, 3 patrols, 1 section. The model supports more sections
and patrols so the app doesn't need reworking if the troop grows.

### Structure

```
Troop
└── Section        (e.g. Πρόσκοποι)
    └── Patrol     (ενωμοτία) × 3
        └── Scout  × ~6
```

## 3. Authentication

Scouts do not reliably have email, so there is no email in the system.

**One passcode per scout.** Login is a single field: an 8-digit numeric passcode
printed as `4821-7302`, unique per scout, that both identifies and
authenticates. Numeric only, so there is no Greek/English keyboard fumbling, and
sessions last months, so it is typed roughly once per device.

- Passcodes are generated by the system, never chosen, and handed out on printed
  login cards.
- Lost card → a leader regenerates the passcode, which voids the old one, and
  prints a new card. There is no "reset PIN" concept — the passcode is the card.
- Storage: a keyed hash (HMAC with a server-side secret) so the login lookup is
  a single indexed query; the plaintext is shown once at generation and on the
  printed card, never stored. With rate limiting per IP (and a global
  circuit-breaker on repeated failures), an 8-digit space is ample for 18 users.
- Session is a sealed, httpOnly cookie via `nuxt-auth-utils`, valid **180 days**
  **[ASSUMED]** — scouts should effectively never be logged out.

**Known and accepted limitation:** a scout who shares their passcode (or loses
the card before reporting it) lets someone else use their passport until a
leader regenerates it. Acceptable for a troop game; it is the reason nothing
sensitive is stored here.

## 4. Technology

| Layer | Choice | Why |
|---|---|---|
| Framework | **Nuxt 4** | Matches the stack we already work in daily; Nitro builds to a plain Node server |
| Server | Nitro `node-server` preset | One small container, no platform lock-in |
| DB | **SQLite** + Drizzle ORM | Single file. Backup is a file copy. Vastly more than 18 users need |
| Auth | `nuxt-auth-utils` | Sealed cookie sessions in a few lines |
| i18n | `@nuxtjs/i18n` | EL/EN with fallback |
| PWA | `@vite-pwa/nuxt` | Manifest, service worker, push subscription |
| Push | `web-push` (VAPID) | Free, no Firebase, no per-message cost |
| Proxy/TLS | **Caddy** | Automatic Let's Encrypt |
| Host | Hetzner VPS, Docker Compose | ~€4–5/month |

All database access happens in `server/` routes. The browser never talks to the
database.

## 5. Bilingual content

UI chrome is fully translated in both languages via `@nuxtjs/i18n`.

For **content** entered by leaders (event titles, achievement descriptions,
challenge questions and options):

- **Greek is required. English is optional.**
- If an English value is missing, the Greek is shown instead. Nothing is ever blank.

This avoids forcing leaders into double data entry, which would kill the tool.
Language preference is per-scout, stored on their record, toggleable in Settings.

| Column | Type | Notes |

**No free-text note field, deliberately.** A uniform check is a judgement recorded
against a named minor; a three-state rating is a fact, a comment box invites
something a parent would not want to read.

### `point_awards`

| Column | Type | Notes |

**Points now come from two places** — `challenge_answers` and this ledger — and a
scout's total is the sum of both. A single unified ledger would be purer, but it
would mean rewriting challenge scoring for no benefit at this size.

## 7. Challenge mechanics

- Multiple choice, exactly one correct answer, optional image.
- **One attempt per scout**, graded instantly **[ASSUMED]**. On answering, the
  scout immediately sees correct/incorrect, the right answer, and the explanation.
- Answering late — after `unlocks_at`, before `closes_at` — still scores **full
  points** **[ASSUMED]**. Nobody is punished for a missed notification, which is
  important given push is unreliable on iPhones.
- After `closes_at`, the challenge is read-only and the answer is visible to all.
- Points are frozen at answer time.

---

## 8. Points and leaderboards

Two tabs, both scoped to the section:

- **Individual** — total points, descending. Ties share a rank.
- **Patrol** — **average points per active member** **[ASSUMED]**, so a larger
  patrol doesn't win by having more people.

Only `is_active` scouts count. Leaders are excluded from both boards.

---

## 9. Notifications

Web push, VAPID keys generated once and stored as env vars.

**Scheduler:** host cron hits a token-protected endpoint (`/api/cron/tick`) every
5 minutes. On each tick:

1. Publish any challenge whose `unlocks_at` has passed → notify eligible scouts
2. Send event reminders whose `remind_at` has passed
3. Prune push subscriptions that have been failing

Announcements are sent manually by a leader from the admin screen.

**iOS caveat, by design:** web push on iPhone only works if the scout has added
the app to their home screen *and* granted permission. It also drops silently
sometimes. Therefore:

- Settings shows clear, illustrated install + enable instructions
- The app shows a gentle in-app banner for an unanswered open challenge, so
  notifications are never the only way to find out
- No game mechanic ever depends on receiving a notification

## 10. Screens

### Navigation structure

Scouts and leaders get **different apps behind the same login**:

- **Scout tabs:** Διαβατήριο · Ημερολόγιο · Προκλήσεις · Κατάταξη · Χρήσιμα,
  with Settings behind a ⚙ in the Passport header.
- **Leader tabs:** Προφίλ · Πρόσκοποι · Δράσεις · Προκλήσεις · Άλλα. The profile
  is the brief card described above; everything else is management. Badge
  awarding, announcements, info-page admin and (troop leader only) Roles live
  under **Άλλα**, so new admin sections never need another tab.
- **Each leader tab keeps its own navigation stack** — Back pops one level,
  switching tabs and returning restores where you were, and re-tapping the
  current tab pops it to its root.
- **Colour signals the mode.** Troop colours are green, yellow and blue: the
  scout app leads with deep sage green, the leader app re-themes the same
  components slate blue, and yellow marks points, badges and the ⊕ action —
  so a leader always knows at a glance which side they are on.
- **Visual language** (see the prototype, which is the styling reference):
  pale sage ground with white cards; deep muted sage/slate gradients for hero
  surfaces; large light-weight numerals for stats; a **floating dark icon-only
  nav pill** with a circular highlight on the active tab; frosted-glass header
  controls, sheets with grabbers, and iOS-style inset hairline separators.
  Typeface: **Commissioner** (Google Fonts, full Greek support), falling back
  to the system stack.
- **Animated welcome.** The login screen opens with the troop mascot — a wolf
  cub in a neckerchief beside a flickering campfire under twinkling stars. It
  bounces in, then idles (breathing bob, blinks, an occasional wave) while the
  title, field and button stagger in. Pure inline SVG + CSS keyframes: no image
  assets, no libraries, and it fully honours `prefers-reduced-motion`. The
  mascot is a code asset like the uniform illustrations, reusable later for
  empty states and the "correct answer" moment in challenges.

### Scout

| Screen | Contents |
|---|---|
| **Passport** (home) | Name, patrol, section, total points, rank; achievement grid — earned in colour, unearned greyed with title visible as something to aim for; banner for an open unanswered challenge |
| **Calendar** | Upcoming list + month view; filter chips: All / Troop / Section / My patrol; tap for detail |
| **Challenges** | The open challenge; history of answered ones with correct answers and explanations |
| **Leaderboard** | Individual and Patrol tabs |
| **Info** | List of reference topics; tap through to a page. Uniforms is the first |

### Leader (additional)

| Screen | Contents |
|---|---|
| **Scouts** | Roster grouped by patrol; tap through to a scout: login card, passcode regeneration, badges held, move patrol, deactivate. Print all login cards |
| **Achievements** | List with "awarded to N/18"; tap to award — pick a completion date, multi-select scouts, award in one action |
| **Events** | List with scope dots; editor with EL/EN titles, scope picker, location, times, reminder toggle |
| **Challenges** | Grouped by lifecycle (scheduled / active / finished); authoring with options editor, image upload, schedule, publish. Tap any challenge for **Results**: per-option answer spread and who hasn't answered, with a "remind them" action |

Mobile-first throughout. Scouts will only ever see this on a phone.

## 10a. Uniform illustrations

The uniform page shows a flat SVG figure for each of the two uniforms
(Επίσημη Στολή and Στολή Εργασίας) with **numbered markers on the drawing that
key to the numbered checklist** beneath it.

Three reasons for that design:

- **No text inside the SVG**, so one drawing serves both languages
- **Inline SVG**, so there are no image files to upload, store or back up
- **No photographs of scouts**, which keeps §12 intact — the figures are
  deliberately faceless and not identifiable

The drawings live in the codebase, not the database, since they change roughly
never. `info_pages.illustration` just names which one to render.

## 11. Infrastructure

Single Hetzner VPS, Docker Compose:

```
caddy      → TLS termination, reverse proxy, serves /uploads
app        → Nuxt/Nitro node server
(volume)   → /data/passport.db  +  /data/uploads/
```

- Ports 80/443 public; SSH key-only, password auth disabled
- `unattended-upgrades` for OS security patches
- Domain required — Let's Encrypt will not issue for a bare IP, and both PWA
  install and push need real HTTPS

**Deploy:** `git pull && docker compose up -d --build` wrapped in `deploy.sh`,
run over SSH. Manual and boring on purpose **[ASSUMED]**.

**Backups:** nightly `sqlite3 .backup` to `/data/backups/passport-YYYY-MM-DD.db`,
14-day retention, plus uploads. **Copying these off the server is a decision still
owed** — a Hetzner Storage Box or a pull to a local machine. Backups that live
only on the box that dies are not backups.

## 11a. Meeting review and points

After a meeting a leader opens the event and works down the roster in three tabs:

| Tab | What it records |
|---|---|
| **Παρουσίες** | Present / absent / excused per scout, grouped by patrol, with a "mark all present" shortcut and a running tally |
| **Στολή** | Full / incomplete / none — **only lists scouts marked present**, since you cannot assess the uniform of someone who was not there |
| **Πόντοι** | Pick the winning patrol, enter points and a reason, award. Awards for the meeting are listed underneath |

### Do attendance and uniform award points?

**[ASSUMED] yes — 5 points each for attending and for full uniform.** This is the
most likely reason to want the feature: it makes the leaderboard reflect turning
up and turning up properly, not just quiz answers. Both values are single
constants; set either to 0 and the record is kept without affecting the ranking.

Patrol awards credit every **active** member, which keeps the patrol leaderboard
(average points per member) fair regardless of patrol size.

Every award carries a reason that scouts can see, so nobody's total changes for
reasons they cannot find.

## 12. Privacy

- Stored per scout: first and last name, patrol, achievements, challenge answers,
  points, attendance and uniform records. Nothing else.
- No photos of scouts, no birthdates, no addresses, no contact details, no email.
- Consent is on file with the troop.
- Leaving scouts are deactivated; full deletion on request is a single admin action.
- The database contains minors' names, so: no public pages, everything behind
  login, and backups are treated as sensitive.

3. **Calendar + info pages** — event CRUD with scopes, calendar screens,
   info page CRUD, uniform illustrations

4. **Challenges + leaderboards** — challenge authoring, answering, scoring, boards
5. **Notifications** — VAPID, subscription flow, cron scheduler, announcements,
   install guidance

Usable by the troop from the end of phase 3; phase 4 is the fun part.
